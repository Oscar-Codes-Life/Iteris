# Iteris 1.2.0 — Finish the backlog

Iteris now keeps working until every ticket is done. When an attempt fails, it no longer stops the ticket or waits for input. It records what went wrong, stops that instance, and starts a fresh one that knows what happened.

## What's new

- **Journal, kill, respawn.** When an attempt crashes, times out, stalls, fails checks or CI, or is blocked by review, Iteris:
  - records the phase, cause, commit, findings and last output;
  - stops the instance;
  - keeps the branch, commits, plan and evidence;
  - reschedules the ticket with backoff and moves on with the queue.

  The next instance receives the ticket together with the history of earlier failures.
- **An attempt journal for every ticket.** Each failure is written to `.iteris/tasks/<key>/attempts.md`, newest first. `iteris status` shows the failure count and the latest cause. Identical consecutive failures are folded into one entry, and the journal stays bounded on tickets that fail many times.
- **Stall watchdog.** An instance that produces no output for `recovery.idleTimeout` seconds (default 1800) is stopped and retried, instead of holding a slot until the full timeout.
- **Partial work is kept.** If a crashed instance left uncommitted changes, Iteris commits them as a checkpoint on the task branch. The next attempt starts from that work.
- **Repair before re-review.** When review blocked the current commit, a repair instance fixes the recorded findings before review runs again.
- **No more Retry/Skip dialog.** The queue never pauses for input. Failed tickets show **retrying** in the Queue and Instances views, and the queue shows when the next fresh instance starts.
- **Tasks are no longer blocked for good.** Blocked reviews, failed CI repairs, workspace and host errors, and exhausted setup budgets now lead to another attempt. A verified task that ran out of time completes after a fresh readiness check. An unexpected error in one task no longer stops the queue.
- **Optional cap.** Retries are unlimited by default. Set `recovery.maxTaskAttempts` to stop a ticket after that many failures. A stopped ticket keeps its journal, and `iteris resume` gives it a fresh budget.

Waits for external evidence and provider outages, such as rate limits, are retried with backoff and do not count as failures.

## Install or upgrade

Let active queues finish, then run:

```bash
curl -fsSL https://raw.githubusercontent.com/Oscar-Codes-Life/Iteris/v1.2.0/install.sh | bash
iteris --version
```

Expected version: `1.2.0`. Requires macOS/Linux, Node.js 22+, Git, GitHub CLI, and an authenticated Claude Code or Codex installation (or configured project-local prerequisites).

No configuration change is required. To tune the loop, add a `recovery` block to `.iteris.json`:

```json
{
  "recovery": {
    "attempts": 2,
    "idleTimeout": 1800,
    "maxTaskAttempts": 0
  }
}
```

| Key | Meaning |
| --- | --- |
| `attempts` | Immediate repairs within one attempt before the ticket is rescheduled (default 2). |
| `idleTimeout` | Seconds without output before an instance is stopped as stalled (default 1800; `0` disables it). |
| `maxTaskAttempts` | Failed attempts before a ticket stops (default `0`, never stop). |

Backoff between fresh instances follows `continuation.initialSeconds` and `continuation.maxSeconds`.

When a ticket keeps retrying, read its journal:

```bash
iteris status
cat .iteris/tasks/<key>/attempts.md
```

Fix any shared prerequisite, switch harness or model with `/model` for the next attempt, or cancel the ticket with `iteris cancel <key>`.

## Compatibility and operating notes

- **Behavior change:** failed tasks now retry until they finish. If a ticket can fail on something only a person can fix, set `recovery.maxTaskAttempts` to limit model usage.
- Configuration remains version 3 and needs no migration. Existing task records load unchanged. Tasks that an earlier version left blocked are picked up again on the next queue or `iteris resume`.
- If you go back to an earlier version, first remove `recovery.maxTaskAttempts` and `recovery.idleTimeout` from `.iteris.json`. Earlier versions reject these keys, and 1.2.0 may write them when it saves settings.
- If a quality check cannot run in your environment, the agent is told to report the exact command and output instead of skipping it. Review still requires passing checks.
- Long-running steps that legitimately print nothing for 30 minutes need a larger `recovery.idleTimeout`.

This is the first tagged release. Version 1.1.0 was prepared but never tagged. 1.2.0 includes all of its changes: parallel worktrees, `.worktreeinclude` copying and the Instances view. See the [1.1.0 notes](https://github.com/Oscar-Codes-Life/Iteris/blob/v1.2.0/docs/releases/v1.1.0.md).

## Verification

Besides the unit and lifecycle tests, CI runs `npm run test:soak`. The soak puts a 20-ticket backlog through the real runner and worker, with scripted harnesses that inject faults: crashed and stalled instances, rate limits, crashes that leave uncommitted work, implementations that review blocks, crashing repair instances and failed CI. It passes only when every ticket completes with one PR each and every fresh instance received its journal. The original 1.1.0 code left 7 of the 20 tickets blocked on the same backlog. Automated tests use scripted harnesses, not live model runs.
