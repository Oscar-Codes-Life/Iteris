# Configurable completion and recovery

Iteris completes a coding task when the published commit has successful local checks, independent review, required CI evidence, all configured acceptance stages, and any configured source update. Publication alone never completes a task. Unfinished work is a draft PR and remains resumable.

Evidence Iteris cannot obtain from a local checkout and that no configured stage verifies (a physical-device session, a hosted service, an attachment the ticket did not supply) is governed by `workflow.externalEvidence`. With the default `advisory`, it is listed in the PR's completion section under **Please verify by hand** and does not hold the task. With `required`, the task waits until a configured probe verifies it or evidence is submitted with `iteris evidence`. A stage declared in `verification.stages` is the operator's requirement and blocks in either mode.

`.iteris.json` version 3 preserves the existing harness, provider, branch, quality-check and PR settings. Version-1 and version-2 files are backed up before migration. A permanent `pr.draft: true` setting remains effective after verification.

## Configuration

Start with [the minimal example](examples/lifecycle-minimal.json). [The extended example](examples/lifecycle-extended.json) shows named behavioral checks, runtime preparation, task profiles, deployment, device and monitoring probes, and a command task source. Replace executable names and credential references with your own commands. The examples contain no automatic deployment to an actual service.

Configuration resolves from defaults, project settings, matching profiles, and explicit CLI execution selections. Profiles match provider, labels and changed paths; checks and stages merge by stable ID. Conflicting definitions fail validation. Path profiles are applied after the actual diff is available. Setup commands must operate within project directories; Iteris never automatically upgrades global harness installations or edits shell profiles.

`verification.maxContextCharacters` limits the combined trusted policy/context text supplied to reviewers (default 40,000, maximum 1,000,000). Raise it when a repository's engineering guide exceeds the default; context is never silently truncated. The limit is checked before any instance starts: an oversized context leaves the task waiting with this instruction instead of failing after implementation, and the next attempt re-reads the configuration. Matching profiles can raise this limit.

Structured commands use `executable`, `args`, `cwd`, `timeout` (seconds), `env` (destination variable → host variable reference), and optional platform variants. An explicit `shell` is required for structured shell execution. Existing string `qualityChecks` retain their historical shell semantics. Model-suggested planning and recovery commands run with local isolation, offline; unavailable isolation is a capability dependency. Only planned commands that serve a local requirement are run as gates: a command planned for review, publication, CI or a later stage cannot pass before that stage exists, and a command naming a policy or context file the base does not have is dropped. A suggested command whose tool is not installed on the host (exit 126 or 127) is recorded as unavailable evidence, not a failed check. So is one that starts a dev server, drives a device or calls the code host (`npm start`, `expo start`, `adb`, `maestro`, `gh`); it is not run. The independent verifier may attribute any other failed suggested command to the host environment (an occupied port, a refused simulator connection, denied network access), which also stops it gating; the review shows the attribution. A configured `qualityChecks` or `verification.checks` command always runs, and one that fails or cannot start is a failure no reviewer can waive. External actions require a configured stage and its ID in `integrations.externalActions`. Ticket or model text cannot enable them.

The preflight manifest resolves runtime paths, versions, probe output hashes and environment references. Host checks and harness processes share its PATH. Only redacted environment metadata is persisted. Configure environment probes for prerequisites whose identity matters to cached checks, such as an installed dependency tree or a local service schema. Configured installers run with project-local filesystem isolation. Missing isolation becomes a waiting dependency; prepare prerequisites manually when the platform cannot provide it.

Claude write sessions use its sandbox with `failIfUnavailable`, a strict network allowlist and no unsandboxed fallback. Codex uses `workspace-write` and no interactive approval requests. Git branch preparation and committing source changes belong to the host, allowing harness sandboxes to protect `.git`. The settings follow [Claude's sandbox documentation](https://code.claude.com/docs/en/sandboxing). Missing platform or sandbox support must be resolved before local repair can proceed; it is never permission to bypass isolation.

## State and completion

Records live in `.iteris/tasks/<key>/run.json`. The key includes destination repository, task provider, source namespace and stable source ID. Display numbers and titles are not identity. The record contains requirements, commit/base evidence, execution metadata, retries, PR details, dependencies and action intents. Writes use a temporary file and atomic rename. `status.md` is a generated view.

States are `queued`, `active`, `waiting`, `blocked`, `complete` and `cancelled`. `blocked` means the attempt cap or disabled recovery stopped the task; tasks blocked by earlier versions rejoin the attempt loop automatically. Execution phase is independent. Waiting dependencies include the missing capability, next action, probe time and persisted retry schedule. Probes start at 60 seconds and back off to 15 minutes. Runnable work takes priority; a repository lock serializes writes. Stopping the foreground process preserves unfinished work. Explicit cancellation prevents resumption.

Planning saves a verification pack before implementation. It includes stable requirement IDs, trusted base policy/context files, fixtures, reproduction strategy, behavioral checks and required capabilities. Acceptance extraction conservatively retains ticket content, except bare labels such as `Acceptance criteria:` and the task-file lines Iteris appends to custom tasks, and recognizes deployment, device, provider, merge and monitoring stages. Use explicit configured stages for precise acceptance semantics and observation durations. Later stages are verified by host probes after publication; local reviewers assess implementation and preparation for them.

Each attempt starts by bringing the task branch up to date with its base: the base is fetched, a branch without task commits is fast-forwarded, and otherwise the base is merged in. Conflicts are resolved by an instance and committed by the host; an unresolved or interrupted merge is aborted and never committed. The attempt then works and is reviewed against that one base commit, even when a parallel task fetches a newer one. A base that moves later invalidates readiness only when the published commit no longer merges cleanly, or when the repository's own rules require an up-to-date branch; the next attempt then merges the base again.

Checks and independent review must cover the final commit. Reviewers judge the ticket's local acceptance requirements with status `covered`, `missing`, `unverified` (evidence a local checkout could produce is absent) or `external` (only observable outside a checkout). The host decides its own gates (local checks, independent review, publication, required CI) and later stages from its own evidence; a reviewer's opinion of them is ignored. Findings block when they are critical or high, concern acceptance, are a material maintainability regression or violate quoted policy; other findings are listed in the PR and do not make a requirement missing. Each review phase is allowed a quarter of `timeout` (at least 15 minutes, 30 in deep mode) unless `review.timeout` is set. Cache keys include task content, base, configured verification and environment identity. Failed checks and incomplete investigations never become completion caches. Every repair commit receives fresh checks and review. Local evidence commands still execute when external dependencies remain. Duplicate findings keep the strongest severity and all blocking obligations; ambiguous duplicates remain unresolved findings. Harness changes to host-owned run records or verification/action configuration are restored and rejected. Live CLI harness, model and effort selections remain available.

Within one attempt, recovery defaults to two immediate repairs within the task timeout, reserving 20% for final verification. Repeated prose cannot reset the budget. Beyond that, a failed attempt is never abandoned: the host appends it to the task's attempt journal (`run.json` `attempts`, rendered to `.iteris/tasks/<key>/attempts.md`) with phase, cause, commit, findings or failed checks and the instance's last output; stops the instance; commits uncommitted partial work as a checkpoint; and records an `attempt` dependency whose retry time backs off from `continuation.initialSeconds` to `continuation.maxSeconds`. The worker then starts a fresh instance with its own allowance and the journal in its prompt. When the last verdict concerned the current commit (blocked review or failed CI), a repair instance runs before review; a repair that changes nothing is followed by a full re-review rather than another identical repair. `recovery.idleTimeout` (default 1800 seconds, `0` disables) kills an instance that produces no output. `recovery.maxTaskAttempts` (default `0`, unlimited) stops a task after that many failed attempts; `iteris resume` grants a stopped task a fresh budget. Dependency waits are journaled but never count toward the cap, and identical consecutive failures fold into one entry. Exhausting the allowance after all evidence passed schedules a fresh readiness check instead of blocking. Failed CI enters local repair, followed by checks and review of the new published commit. CI verification uses explicit required names when configured, otherwise branch-protection and ruleset discovery; a branch covered only by rulesets has no classic protection, which is not a discovery failure. Discovery failures remain visible. A changed published head, or a base change that conflicts with the published commit, invalidates readiness and triggers reconciliation.

## Adapters and action protocol

Task sources and publication are separate. GitHub Issues/Projects, full Trello card IDs and custom imports supply tasks; GitHub publishes PRs. Other systems use `integrations.source` with a command adapter. Each request is one JSON object on stdin, version `1`. Emit one JSON object on stdout; write diagnostic logging to stderr.

Source requests have `operation: fetch | refresh | synchronize`, repository, source identity, and relevant task/run/publication fields. A successful response is `{ "version": 1, "ok": true, ... }`. Fetch adds `tasks`; refresh adds `task`; synchronization adds `verified: true` and optionally a receipt. Each task has `id`, `number`, `title`, `body`, `labels`, and `url`. Refresh must return the same source ID and namespace. Credentials stay in configured host environment references.

External stages have separate `execute` and `verify` commands. Verification requests include operation ID, requirement IDs, commit, base, run key and publication. A verified receipt is:

```json
{"version":1,"verified":true,"commit":"<published SHA>","observedAt":"2026-09-30T12:00:00.000Z","build":"optional build ID","details":"provider receipt or observation"}
```

A nonzero probe exit or `verified: false` means evidence is pending. Invalid, truncated, wrong-commit or future-dated evidence does not satisfy a stage. Monitoring records observations across probes for the configured window; failed probes reset the window. Device stages can use probes or explicitly submitted evidence. The PR body has three generated parts, each replaced in place: the description, the independent review and a completion section. The description is written by the harness from the final diff once the review passes, also when the PR was opened earlier as a draft with a placeholder; `iteris describe [key]` rewrites all three parts for an already published PR (`--dry-run` prints the result instead). A description that already covers the published commit is kept and only the other two parts are rendered again, which needs no harness call; `--rewrite` forces a new description. `iteris describe --all` also covers pull requests from earlier queues, open, merged or closed, whose runs are no longer on this machine. One that still carries a placeholder gets a description written from the diff GitHub holds; text a person added above it is kept. For the rest, and without a harness call, the long lists older versions published are folded where they stand and a page-long verdict is cut to its first sentence. Home-directory paths are shortened to `~` in everything Iteris publishes. The review keeps its verdict, open findings and unverified areas visible and folds the per-requirement, per-command and fixed-finding lists. The completion section states where the task stands, what is not yet verified, what is waiting and what a person must verify by hand; requirement identifiers, the evidence log and the attempt history stay in the local `status.md`.

The host persists action intent and operation ID before executing it. After interruption it probes the outcome first. Ambiguous non-idempotent operations remain waiting rather than being repeated. Changed ticket content invalidates planning and evidence while preserving unresolved action intent. Source synchronization uses the same durable outbox. Trello updates target the full card ID and verify the board/list afterward. Missing cards or lists are visible dependencies. Optional GitHub/custom status mappings use configured commands; provide an idempotent mapping or a reliable verification command.

## Commands and migration

```sh
iteris                         # select work, then foreground continuation
iteris --once                  # one scheduling pass
iteris status                  # requirements, dependencies and provenance
iteris resume --once            # refresh and retry unfinished work, including blocked work
iteris doctor                  # inspect prerequisites without running installers
iteris evidence <key> receipt.json
iteris describe [key]           # rewrite the description, review and completion parts of published PRs
iteris describe --all           # also heal older PRs, merged or closed, that still carry a placeholder
iteris cancel <key>
```

Submitted receipts contain `version`, `requirementId`, `commit`, optional `build`, `observedAt`, `provenance`, `details`, and `success`. They can satisfy external requirements; they cannot substitute for local checks, independent review, publication or required CI. Monitoring submissions must span the configured observation window with matching provenance and build. Use `iteris status` to obtain the task key and requirement ID. Evidence updates use the repository writer lock; cancellation records a separate intent and stops active harness or stage execution without overwriting it.

Normal startup imports identifiable legacy artifacts conservatively and reconciles unfinished work. Legacy `done` with blocked/incomplete review is unfinished. Original artifacts remain intact, existing PRs are reused, and committed implementation is preserved when task identity/content match. Legacy Trello display IDs must resolve uniquely through the configured board before any external update. Unidentifiable legacy folders remain intact for explicit reconciliation.

There is no daemon or additional built-in code host. Continuation runs while Iteris is foreground. Merging is an observed external acceptance stage and requires a configured probe; an execution command requires explicit project authorization.

## Verification and rollout

Run `npm run typecheck` and `npm test`. Tests use temporary repositories, scripted Claude/Codex harnesses, mock provider APIs, fake probe schedules and fixture command adapters. Default tests perform no provider writes or deployment. `iteris status` exposes verified completion, current-commit evidence coverage, repair/setup attempt counts, elapsed time and typed waiting dependencies; the PR shows the summary a reviewer needs. Use these measures to evaluate completion rather than counting PRs.

The Roxbase regressions assert that mixed local/external recovery executes local checks and reviews the final commit, unchanged-HEAD dependency recovery is reevaluated, and mixed-severity duplicates reach repair without losing severity. Lifecycle fixtures measure verified completion, correct waiting, current-commit evidence and bounded convergence, including restart and interrupted outbox actions. The historical audit and its original diagnostic artifacts remain in `docs/audits/roxbase-2026-09-30`.
