The analysis supports changing the orchestration, evidence handling, and project execution environment before changing models. A stronger model could still encounter the same deterministic exits. **Opening the PR currently terminates responsibility for the task.** In [runner.ts](/Users/oscargallo/programming/OscarCodesLife/Iteris/src/agent/runner.ts:145), a blocked or incomplete review proceeds through publication. The result is assigned to `reviewPending`, but the state becomes `done` at line 194. The queue’s recovery loop only handles `failed`, `stale`, `blocked`, and `incomplete`, so it never recovers these published tasks. [TicketPicker.tsx](/Users/oscargallo/programming/OscarCodesLife/Iteris/src/ui/TicketPicker.tsx:27) also leaves unchanged `done` tasks unselected on the next run.

This behavior was introduced deliberately in the September 24 commit [875eca6](https://github.com/Oscar-Codes-Life/Iteris/commit/875eca6), titled “Open PRs and advance queue after incomplete reviews.” The subsequent [389a1b7](https://github.com/Oscar-Codes-Life/Iteris/commit/389a1b7) added unfinished-review reuse, and [cf6f2af](https://github.com/Oscar-Codes-Life/Iteris/commit/cf6f2af) permitted incomplete publication after remote-base advancement. These changes improved queue throughput, but they made publication the terminal state even when task completion remained outstanding. This explains the recurring pattern without requiring an exceptional model failure.

Publishing unfinished work can be useful when CI needs a PR or a human needs something concrete to review. Keep that capability, with a distinct `draft_published` or `awaiting_ci` state and a durable continuation record. Queue advancement and successful task completion must be separate decisions. Unfinished work should retain its blocker, next executable action, evidence requirements, and resumability. The inspected configuration uses `pr.draft=false`, and the current API reports all 14 PRs as non-draft; the code does not automatically make an unfinished review draft.

**Mixed local and external gaps short-circuit the recovery loop.** The decisive ordering is in [reviewer.ts](/Users/oscargallo/programming/OscarCodesLife/Iteris/src/agent/reviewer.ts:227): Iteris captures the post-recovery commit, checks `recovery.blockedReason`, and throws before adding `recovery.checks` at line 239. A remaining external blocker therefore suppresses independent review of a new source commit and the host execution of available local tests. The report keeps the previous round’s commit and checks.

This occurred in eight tasks. Seven of those recoveries changed the branch head; the device investigation did not. For example, password revocation was reviewed at `55563ce1`, recovery committed `2bd4d523`, and the published branch contained the latter. The recovery returned unit, typecheck, integration, and app test commands, alongside pending deployment receipts. None entered the final host evidence. The Fold, stale-detail, subscription recovery, benchmark replacement, signup fallback, and AMRAP cases followed the same pattern.

Fix the contract to distinguish `localChecks`, `sourceChanged`, and typed external dependencies. Always preserve and execute the returned local checks, then independently review every source change. Record remaining external requirements after that review. A task may be locally ready and awaiting delivery at the same time. If a local defect remains, it stays blocked; completing the available work does not waive device or production acceptance.

**The current review contract cannot represent staged acceptance.** Ticket requirements are reduced to `covered`, `missing`, or `unverified`, with no stage, prerequisite, or owner in [schema.ts](/Users/oscargallo/programming/OscarCodesLife/Iteris/src/review/schema.ts:12). This makes “run local regression tests,” “record the PR,” “deploy the app,” “perform a store purchase,” and “observe Sentry for seven days” look like simultaneous prerequisites. Yet the review protocol prohibits publication and production mutation. Password revocation literally became blocked on recording a PR that the host had not created yet. The stale-detail task explicitly said its post-publication evidence was not a prerequisite to opening the PR, but the host still terminated local recovery on that evidence.

Represent requirements with stable IDs, source provenance, an acceptance stage, a verification method, and dependencies. Useful stages are source implementation, local verification, hosted CI, merge/release, device/provider verification, and observation. Represent outcomes independently for each stage. Resolve product-wide completion only when all required stages are satisfied; do not label a seven-day observation complete on the first day. An operational task such as enabling signup fallback must have an operational execution path, or remain visibly awaiting the missing authority and environment.

**Retries currently have two conflicting meanings.** [loadUnfinishedReview](/Users/oscargallo/programming/OscarCodesLife/Iteris/src/review/report.ts:66) returns an old failure report as a publication cache. The runner uses it before calling `runCodeReview`. A manually reselected task can therefore republish the same incomplete report without attempting newly available checks, even though `runCodeReview` has good checkpoint support for continuing investigation. Its cache key includes code and policy inputs, but not whether a phone is now connected, a runtime has been fixed, or external evidence has arrived.

Keep successful evidence caching and per-pass checkpoints. Separate “show/publish the saved report” from “resume unfinished work.” A resume command should refresh dependency availability, rerun failed checks, execute pending commands, and reuse only successful evidence whose inputs still match. Store typed waiting conditions with an evidence timestamp. Environmental recovery should wake the task even when the source commit has not changed.

**The environment repair was not durable for the host.** The configured quality checks were native-version validation, app typecheck, lint, format, and a Deno version-plus-typecheck command. They contained no app, Edge, or PostgreSQL behavior tests. At the start of the run, the Deno command required 2.9.7 while the process resolved 2.7.14. Both #426 and #428 ultimately had no blocking findings and no missing requirements, but failed this command.

Agents downloaded Deno 2.9.7 into temporary directories and supplied passing checks using that binary. Iteris still ran the original configured command through its unchanged PATH, then counted its failure against the task. In #428, the final report includes the original failing command and a successful equivalent temporary-binary command. This is environment inconsistency, not proof that the patch failed its Deno typecheck. Installing the correct version in an agent subprocess did not establish a shared host execution environment.

Give Iteris a project preparation step that resolves exact executable paths and versions for Node, Deno, PostgreSQL, Supabase CLI, and native tooling when required. Pin these in an execution manifest used by implementation, checks, and recovery. Fail preflight once for a known incompatible environment, rather than rediscovering it in every ticket. Report the executable, version, and failing step separately; the `grep` version guard hid useful diagnostics. Use path-scoped checks so a small app-only change does not spend repair cycles on unrelated Edge tooling, while retaining all genuinely required repository gates.

Have planning return required behavioral commands before implementation starts. The host should run those on the committed result and include their actual outputs in the review input. For these tasks, the needed commands already existed or were returned during recovery. Repeatedly asking the reviewer to discover them after static checks added latency and made locally testable work look unverified.

**A valid safety guard became a terminal review error.** In #430’s sixth round, the verifier marked “A stale settings cache can turn off a known enabled chime” as a duplicate. That finding was high severity; its canonical “An older cache value can override a fresher Timer Sounds read” finding was medium. The evidence described the same preference downgrade. [reviewer.ts](/Users/oscargallo/programming/OscarCodesLife/Iteris/src/agent/reviewer.ts:184) rejected this with “Deduplication cannot downgrade a blocking finding.” That protects against losing a blocker, but the host converts the semantic inconsistency into a terminal incomplete result before the next repair.

Preserve the maximum severity and all acceptance/policy obligations in a verified duplicate group. If equivalence is uncertain, request a bounded verifier correction or retain both findings as unresolved. A disagreement over canonical severity should not erase the review or prevent repair. Keep candidates and decisions in the final diagnostic report even when verification normalization fails. This is separate from malformed JSON recovery: the JSON parsed correctly here.

Repairs progressively covered early-start persistence, preserving future removals and duration edits, retaining moved completed workouts, preventing duplicate moved workouts, scheduled-date verification, and preserving early-start evidence. Give complex tasks an invariant and scenario matrix before coding. For generation, run the actual engine plus atomic PostgreSQL persistence through early start, moved-in/moved-out workouts, repeated moves, deletion, duration edits, completed/started rows, rollback, saved versus device timezone, and takeover by a newer owner. For access, drive the real resolver/store/gate across session truth, account identity, entitlement truth, and delayed responses. For notifications, exercise cache/network/local preference ordering and app/native alert ownership together. Add a regression at the seam that proves the full causal path; a leaf helper test alone will not catch an interaction several layers later.

The recommendation is to build these fixtures from the historical failures and existing regression suites. It is not to add a blanket large test suite to every small ticket. The two-file #431 task completed quickly, while the more complex #434 also completed once the necessary cases were covered. Iteris can finish useful work; its success depends on a runnable verification seam and a convergent task model.

**The apparent two-cycle setting is not a total repair limit.** `maxRepairCycles` is constrained to 0–2 in the configuration schema, but [canRepair](/Users/oscargallo/programming/OscarCodesLife/Iteris/src/agent/reviewer.ts:58) counts attempts per failure signature. Signatures include finding IDs derived from title and trigger text, requirement strings, and gap prose. New defects or new wording can open another allowance. This explains eight and nine cycles under a configured value of two; it is not evidence that the configuration was ignored.

Preserve the ability to repair genuinely new defects, which helped #434 pass. Make the limits honest and explicit: attempts per issue, total task effort, and reserved final verification time. Track stable defect and requirement identities, distinguish unchanged failure from new evidence, and trigger replanning when several repairs revisit one invariant. Reserve a configurable portion of the deadline for final checks and independent acceptance review. Increasing timeout alone would not fix the eight immediate external-gap exits, the Deno mismatch, or the duplicate exception.

**The repository’s engineering policy is not fully expressed in the review gate.** All 14 context records have an empty `policy` field. The host loads policy only from trusted-base `REVIEW.md`, while Roxbase’s large `AGENTS.md` contains its engineering bar and domain invariants. Codex can encounter AGENTS.md in the snapshot, so this does not mean it had no repository guidance. However, a structured `policy` finding must quote base REVIEW.md, and the validator rejects an unsupported quote. The trusted structured policy path therefore cannot directly enforce the AGENTS.md engineering bar. #428 subsequently received a human request to replace upward-relative imports and Jest mocks with the mandatory aliases.

Give the review system a concise trusted-base policy that maps engineering rules and relevant domain invariants to paths and checks. Either explicitly include selected AGENTS.md rules in the captured policy or maintain a synchronized REVIEW.md. Keep the full engineering guide available for context, with focused task packs identifying authoritative callers, migrations, test fixtures, and verification commands. Adding another large general prompt would increase reading work without resolving policy provenance or runnable evidence.

Memory also needs improvement. [expandPrompt](/Users/oscargallo/programming/OscarCodesLife/Iteris/src/agent/prompt.ts:28) feeds previous progress lines into the next task. Those lines mainly say a PR opened and identify its final blocker. They do not provide a durable runtime repair, a runnable fixture, or a verified invariant learned from an earlier repair. Persist validated project facts with evidence and scope, then retrieve them for related tasks. Do not turn every model finding into a permanent rule.

A useful machine-readable task pack would contain the task’s intended user outcome, requirement IDs and original evidence, applicable engineering/domain invariants, reproduction command and fixture, exact runtime manifest, local check commands, needed capabilities, external acceptance stages, and the next action for each waiting stage. For account recovery, include approved dialog copy and provider settings evidence. For native bugs, include viewport/text/device configuration and seeded examples. For operational tasks, include current scheduler/deployment identities and permitted test resources. Keep secrets in configured credentials; capture capabilities and receipt identities in task state.

An unfinished PR also deserves a concrete description: what works, what changed, checks on the current commit, confirmed defects, remaining evidence, and the next action. The current incomplete path writes “See the commits in this pull request” instead of using the PR-description step. That saves a model call but makes the handoff harder to finish. A deterministic description from structured task and evidence state can provide the missing detail without relying on another narrative model.

**Validate the redesign against historical completion, not PR count.** The current evaluation corpus is explicitly synthetic and focuses on reviewer behavior; it does not establish end-to-end ticket completion. Preserve the existing tests for independent review, dirty/stale snapshots, failed checks, and repair resolution. Add the actual combined cases this run exposed: new commit plus local commands plus external blocker; a recovered environment at unchanged HEAD; mixed-severity duplicates; CI that requires PR publication; genuine physical-device investigation; native fixture setup; and a long generation task that must finish validation before its deadline.

Measure locally complete tasks, correct waiting-stage classification, current-head test/review coverage, later confirmed defects, human repair work, elapsed time, and usage when available.
